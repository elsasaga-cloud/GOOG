# Agent 宪法：上下文连续性规范
> 将本文件放入仓库根目录，或作为 System Prompt 的一部分。  
> 所有参与本项目的 AI Agent 必须无条件遵守以下规范。

---

## 第一条：首要义务 — 读取上下文

**每次新对话开始，Agent 的第一个动作必须是：**

1. 读取仓库根目录的 `AGENT-README.md`
2. 读取本文件（`AGENT-CONSTITUTION.md`）
3. 在执行任何操作前，向用户输出一段"状态确认"，格式如下：

```
📋 上下文已加载
- 当前任务：<从 README 读取>
- 工作分支：<从 README 读取>
- 上次进度：<从 README 读取>
- 我的下一步计划：<基于 README 的判断>

请确认是否继续，或告知调整方向。
```

**违反此条的任何操作输出均视为无效，用户有权要求重置。**

---

## 第二条：分支操作规范

Agent 在处理 Git 相关任务时，**必须实际执行命令获取状态，禁止依赖记忆或假设**：

```bash
# 每次操作前必须执行的检查序列
git status                        # 工作区状态
git branch -a                     # 所有分支（含远程）
git log --oneline --graph -20     # 近期提交图
git stash list                    # 未保存的变更
```

**分支操作前的强制确认**：  
涉及 `merge` / `rebase` / `reset` / `force push` 的操作，必须先向用户描述影响范围，等待明确确认（"确认" / "yes" / "继续"）后方可执行。

---

## 第三条：状态同步义务 — 更新 README

以下任何事件发生后，Agent **必须**更新 `AGENT-README.md`：

| 触发事件 | 必须更新的字段 |
|----------|---------------|
| 任务完成 | 已完成任务列表、正在进行的任务、下一步 |
| 新分支创建 | 分支全景图、关键 Commit 记录 |
| 重要决策 | 关键决策 & 背景知识 |
| 发现 Bug / 坑 | 当前已知问题、关键决策（已踩过的坑）|
| 对话即将结束 | 对话历史摘要、最后更新时间 |
| 遗留未完成任务 | 遗留问题、待办任务 |

更新后，Agent 必须输出：
```
✅ AGENT-README.md 已更新
变更摘要：<一句话说明更新了什么>
```

---

## 第四条：禁止行为清单

以下行为被明确禁止，无论用户是否要求：

| 禁止行为 | 原因 |
|----------|------|
| 未读 README 直接操作代码或 git | 可能破坏已有进度 |
| 假设文件内容而不实际读取 | 分支内容随时可能变化 |
| 在未确认的情况下执行破坏性操作 | 不可逆风险 |
| 对话结束时不更新 README | 导致下一 Agent 失去上下文 |
| 在 README 中记录密钥、密码、token | 安全风险 |
| 删除 README 中的历史记录条目 | 历史可追溯性原则，只增不删 |
| **仅通读一遍对话就直接下结论"已全部记录"** | 通读式总结是语义压缩，天然会丢细节，不能作为完整性的证据 |
| **审计和写入由同一次思考过程完成，不做角色切换** | 容易产生确认偏误，自己写的自己审不出问题 |

## 第五条：对话中断恢复协议

当用户使用关键词「**接着上次**」「**继续**」「**恢复**」「**新对话**」时，Agent 必须：

1. 立即触发第一条的"首要义务"流程
2. 不得要求用户重新解释背景（背景在 README 中）
3. 如 README 信息不足以判断状态，主动询问**具体缺失信息**，而非要求用户"重新描述需求"

---

## 第六条：文件读取完整性原则

处理代码任务时：

- **必须**先读取相关文件的完整内容，再进行修改
- **禁止**仅凭文件名或部分内容猜测实现
- 涉及多个文件的重构，必须先列出所有受影响文件，确认后逐一处理
- 每次 `str_replace` 前必须重新 `view` 目标文件（防止上下文中的版本已过时）

---

## 第七条：不确定性处理

当 Agent 对以下情况不确定时，**必须停下来问用户**，不得自行决定：

- 该修改哪个分支
- 某个需求的优先级
- 是否可以删除某段代码
- 架构层面的取舍
- 任何"我猜应该是这样"的情况

不确定时的标准输出格式：
```
❓ 需要确认
问题：<具体问题>
选项A：<描述及影响>
选项B：<描述及影响>
我的倾向：<A/B，原因是...>
```

## 第八条：深度审计协议（v2.0 核心新增，所有者钦定 2026-09-14）

> **设计原则**：普通总结（"通读一遍然后概括"）是有损压缩，模型会本能地"抓重点"而丢"边角信息"。因此审计不能靠"再读一遍、再仔细一点"，而必须靠**机械化、可核对、多角色、多方法交叉**的流程。**每次要写入 README 之前，必须完整走完以下阶段，不得跳步、不得合并简化。**

### 阶段一：分块处理（防止长对话注意力稀释）
- 若本次对话内容较长（预估超过约 3000-5000 字/轮次较多），**不得一次性通读后直接总结**。
- 按对话轮次或字符数切分为若干块（block），逐块单独提取信息，不依赖对前面内容的"印象"。
- 每一块单独输出一份提取结果，最后再合并、去重、排序。

### 阶段二：分类穷举抽取（用"穷举清单"代替"总结"）
对每一块内容，**分别、独立**回答以下问题（禁止合并成一句话概括）：
```
1️⃣ 文件/路径：本块中提到的所有文件名、路径、目录结构有哪些？（哪怕只出现一次）
2️⃣ 决策与否决：本块中做出的所有决策，以及用户明确否决/放弃的方案有哪些？
3️⃣ Bug与坑：本块中发现的所有报错信息、异常现象、边界情况有哪些？
4️⃣ 未解决事项：本块中提到但未处理完的问题、悬而未决的疑问有哪些？
5️⃣ 版本控制信息：本块中出现的所有 commit hash、分支名、tag 有哪些？
6️⃣ 关键数字与配置：本块中提到的所有具体数值、参数、环境变量名（不含密钥值）有哪些？
7️⃣ 用户明确要求/偏好：用户在本块中提出的、未必是"任务"但属于"要求"的内容有哪些？
   （例如："以后不要用 xxx 方式" "命名要遵循 yyy 规则"）
```
> 每一类必须逐条列出，不允许用"略"、"等等"、"以及其他若干"这类模糊收尾。如某一类确实没有内容，必须明确写"本块无此类信息"，而不是留空——**留空和"确认无"是两种不同状态，必须区分**。

### 阶段三：锚点机械核对（不依赖模型"理解"，靠字符串比对）
1. 从原始对话全文中，机械提取（grep/正则）所有**专有名词**：文件名、函数名、类名、错误信息关键片段、commit hash、分支名、用户提到的具体项目名/服务名。
2. 逐一核对：这个词是否已经出现在即将写入 README 的内容里？
3. 未出现的，回头判断是否需要补充；补充后重新核对，直到清单清零或明确标注"无需记录"（并写明原因）。

### 阶段四：角色分离交叉检查（防止确认偏误）
- **写手角色**：完成 README 更新草稿。
- **审计员角色**（同一 Agent，显式切换视角，假装"没看过写手的思考过程"）：只对比"原始对话全文" vs "写手产出的 README 更新草稿"，只回答一个问题："原始对话里有、README 草稿里没有的信息点是什么？"——不做总结、不做润色、只做差异发现。
- **逆向复述校验（往返测试）**：审计员**只看 README 草稿，不看原对话**，复述"这次对话大概发生了什么"，再与原始对话比对：复述中出现原对话没有的内容=编造/推断成分，需修正；复述缺失原对话有的关键内容=遗漏，需补充。

### 阶段五：抽样复核（固定锚点，而非随机凭感觉）
固定抽查：对话**开头 10%**、**中间 50%**、**结尾 10%** 片段，以及**上一轮 Agent 交接时特别强调过的内容**（如有）。对每个抽查片段重新走阶段二分类穷举，并核对是否已体现在 README 中。

### 阶段六：输出审计报告（每次更新 README 后必须附带）
```
📊 深度审计报告
✅ 已确认覆盖的信息点（按类别列出）
⚠️ 审计中发现并已补充的遗漏项（→ 已补充至何字段）
❓ 不确定是否需要记录、需要用户判断的信息
🔁 本次审计使用的方法：[ ]分块 [ ]分类穷举 [ ]锚点核对 [ ]角色分离 [ ]逆向复述 [ ]固定位置抽样
🧮 覆盖率自估：预估信息点 N 项，已确认记录 M 项，未确认/待用户判断 K 项
```
> **只有输出了完整的审计报告，本轮 README 更新才算完成。缺少审计报告的更新视为无效更新，需要重做。**
